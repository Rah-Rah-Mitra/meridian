# Meridian v0.6.5 — the two deferred bets, resolved

The v0.6.0 carry-closure release deliberately deferred two bets to a dedicated
session: **C1 claim-level corroboration** (which carried a kill criterion) and
**V1 filtered ANN** (which needed a heavy build and a fresh measurement). Both are
now resolved, experiment-first — one shipped, one recorded as a first-class NO.
Full bench records in `docs/plan/bench/`.

## C1: claim-level corroboration — SHIPPED, default-ON (PR #32)

`GET /v1/search?…&answer=true` now attaches `best_passage.corroboration`
(`schema: 1`; `best_passage` → `schema: 2`): the count of **independent evidence
clusters** — distinct ADR-18 derivation clusters, never the winner's own — whose
top passage the cross-encoder finds states the same claim.

```json
"corroboration": { "schema": 1, "independent_clusters": 2,
  "supporting_urls": ["…","…"], "basis": { "candidates_checked": 5, "method": "ce-cross-cluster" } }
```

**Same-cluster syndicated copies are excluded by construction** — a wire story
reprinted across fifty outlets counts once, never as corroboration. The badge
means *k genuinely independent sources discuss this claim*, not *k copies*, and
not *the claim is true*. `basis.candidates_checked` is the honesty payload: thin
coverage degrades to a low count, never a false badge.

The kill criterion drove the work — *a false "k independent sources agree" badge
is worse than none*. So the suite-20 `answer_trust` judge was rebuilt from its
synthetic `support_score` arm to the **real production signal**: real claim text →
the shipped `meridian_index::sketch` clustering → the **real ort INT8 ms-marco
cross-encoder**. It cleared, on-device, every gate: cluster precision **0.98**
(tuning / hold-out / style-shift; MDE₈₀ 0.031), recall **1.0**, and **zero
same-cluster leakage** on real text. Budget re-checked honestly: the extra CE
batch measures **312 ms p50** (not the design's ~10–20 ms guess — ms-marco INT8
is ~60 ms/pair on the A76), so answer p50 ≈ **2813 ms ≤ 3.0 s**; the CE deadline
is capped at 450 ms and an overrun thins the count, never inflates it.
Record: `docs/plan/bench/2026-06-13-pi5-c1-corroboration.md`.

Knobs: `search.answer_corroborate` (default true), `search.answer_corroboration_tau`
(default 3.0, corpus-specific — re-derive from your own `answer_trust` run). Active
in the cross-encoder (deep/ort) build; dormant in the scratch appliance image,
which doesn't run answer mode (ADR-02).

## V1: filtered ANN — RECORDED NO; the ADR-10 tradeoff was right (PR #33)

Geo/time-filtered queries drop the dense lane (BM25-only, the recorded ADR-10
tradeoff). The gate was **measure the harm first**. The binding evidence is the
real corpus: the dense lane adds only **+0.85 pp nDCG@10 UNFILTERED**; a filter
only *restricts* candidates, so the filtered harm is ≤ that, well under the 2 pp
bar. (A synthetic corpus cannot measure the harm magnitude honestly — it is a
linear function of the chosen lexical/semantic mismatch rate — so the decision is
anchored to the real measured gain, not a manufactured number.) **The dense lane
is not restored under filters.**

The new suite 21 `ann_filtered` instead proves the implementation is *ready* if a
real geo-eval ever flips the call. Two corrections to the bet's premise fell out
of it: usearch 2.25.3 exposes a filter callback **without a fork** (the ADR-07
kill-gate does not fire — `VectorStore::filtered_search` ships), and the exact
INT8 scan (`VectorStore::exact_scan`) retrieves **every** f32 dense neighbour
(recall@20-vs-f32 = 1.0). Both ship unused; no fork, no vector-budget bust.
Record: `docs/plan/bench/2026-06-14-pi5-v1-filtered-ann.md`.
