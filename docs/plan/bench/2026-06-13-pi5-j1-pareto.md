## Caveats that bound these conclusions (read before acting)

1. **ANN ef=64 provenance conflict — resolve before treating "ef64 dominated" as final.**
   Two 1M runs disagree on the exact setting §11.6 calls out:
   `2026-06-10-pi5-ann-final.json:33` reports ef64@1M recall **0.98** (gate-passing),
   while `2026-06-13-pi5-p10-ann-1m.json:23` reports **0.94** (gate-failing). The roadmap
   (`02-budgets.md:149`, `ann-1m.md`) treats the 06-13 Profile-F run as authoritative
   ("ef=64 decays to 0.94 at 1M"); this synthesis follows that, but a single authoritative
   re-run should settle it before the "dominated" verdict is published as policy.
2. **VoI / OPE numbers are DEBUG builds** (`p9-voi.json:14`, `p9-ope.json:13`:
   "DEBUG BUILD — numbers are meaningless; use the CI release-bench artifact"). The
   quality/fetch and bias/variance ratios are *algorithmic* (build-independent), but there
   is **no per-arm wall-clock ms** for the VoI ladder — only fetch counts — so the VoI row is
   a (quality, fetch-count) frontier, not (quality, latency-ms).
3. **Answer-cap quality evidence is n=9 realized winner positions** (`answer-cap-study.md:30`);
   suite 18 does not model passage position, so the device measurement is the only arbiter —
   the cap-8 win is real but lightly powered on the depth-loss side (1/9 queries loses depth).
